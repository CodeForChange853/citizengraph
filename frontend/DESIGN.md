# Design decisions

Record every decision here. Stage 1 (scaffold, tokens, contract, design page) is written; later stages append.

## Why it looks like this (weaknesses of the reference app we design against)

1. Login wall (PIN) before any value -> **no login anywhere**; saved checklists stay on the device.
2. Directory-first (icons by agency type) -> **intent-first** ask box; offices are secondary.
3. Jargon in headings (NGAs, LGUs, MPIN) -> plain words; acronyms spelled out.
4. Rows show a logo and a vague line, no requirements, fee or time -> every row/answer has an **information scent** line.
5. Noise (large illustration, promo banner, "New" badges, flag imagery), small low-contrast grey text -> one small illustration at most, no promo, AA contrast, 16px body minimum.
6. Small targets, floating QR button, plain-bullet AI answers -> 44px targets, three nav items, structured answer card.

Nothing (layout, illustration, name, asset) is copied from the reference. The screenshot stays in `frontend/reference/` (git-ignored).

## Colour

- Palette (`src/design/tokens.json`, the single source): blue `#0038A8` with a tint scale, navy `#0B1F4B` for text, red `#CE1126` (alerts and errors only), yellow `#FCD116` (accent), soft blue-grey neutrals. Tailwind's default colours are removed, so nothing else can be used.
- Rules checked by `npm run contrast` and a vitest test: yellow only on blue/navy or as a background with navy text; never red on blue; every palette entry stays in its hue family; **60 fg/bg pairs pass AA** in light and dark (4.5:1 text, 3:1 UI). A test also rejects raw hex/rgb in components.
- Roles are semantic (`bg`, `surface`, `fg`, `primary`, `notice-bg`, ...). `tokens.css` is generated by `scripts/gen-tokens.mjs` (`npm run tokens`, run by dev/build/check).
- Success and info use blue with an icon. The "being verified" notice is calm: yellow tint with navy text and a navy icon in light mode; a blue-800 card with a yellow icon in dark mode. It is not red because nothing is wrong.
- Alerts (red) always use a light red-50 card with navy text and a red icon, in both themes, because red text on dark blue fails contrast.
- Dark mode follows the phone by default; the Display control offers Match my phone / Light / Dark. In dark mode the primary button is light blue with navy text, and the focus ring is yellow (allowed: on blue).
- Meaning is never colour-only: selected chips show a check mark, ticked boxes a check, notices an icon.

## Type and size

- Font: Atkinson Hyperlegible (designed for legibility), bundled through `@fontsource` (latin 400 and 700), system fallback. No Google Fonts, works offline.
- Scale in rem: caption 0.875 (tags and labels only), body 1 (16px minimum), lead 1.125, title 1.375, heading 1.75, fact 1.5 bold (key facts such as fees and time).
- Text size setting: Normal 100%, Large 118.75%, Extra large 137.5% on `<html>`, saved on the device. Everything is in rem so it all scales.
- 44px tap targets (`min-h-11 min-w-11`), visible 3px focus outline, `prefers-reduced-motion` respected (CSS and Motion's `reducedMotion="user"`).

## API contract (backward compatible)

- `Section` gains `info_status`, `summary {requirement_count, fee_text, time_text}`, `related[]`. New `GET /services`. Nothing removed.
- `pending_lgu` sections carry **no numbers** from the API and the UI hides numbers again if any arrive (test).
- Null means "the charter does not say": shown as "fee not listed", never "free" or a guess.
- Retrieved facts stay in the charter's English wording in both languages; only surrounding sentences are translated (rule 2 and rule 8: no faked Filipino).
- Fixtures are generated from the Python mock (`python frontend/scripts/export_fixtures.py`) so there is one source of mock data. `tests/test_api.py` checks the committed file is current, and a vitest parity test runs the TypeScript router on the same messages as the Python one.
- The API client has two adapters. The real one uses `/api` (Vite proxy). Any network error, timeout or 5xx switches to fixtures and retries the API after 30 seconds. `VITE_USE_FIXTURES=1` skips the API.

## Mock content (from `graph/seed/*.yaml`, needs_review data)

Business Permit (BPLO-01), Sanitary Permit (CHO-10), Medical Certificate (CHO-15), Referrals (CSWDO-01), Birth Registration timely (LCRO-01), Death Registration timely (LCRO-06).

- **LCRO-01 and LCRO-06 are both `pending_lgu`.** The brief named only Death, but `CLAUDE.md` says neither may reach citizens until the LGU confirms, so Birth is pending too.
- Business Permit shows **14** checklist items, not the charter's 9 numbers: items that depend on business type are listed as separate lines with the charter's own prefix ("Single Proprietor:", "Corporation:"). A note tells the citizen to bring the ones for their business. "Corporation: CDA" is the charter's wording (probably Cooperative; unconfirmed, not changed).
- Fee total ₱235.50 equals the four step fees (test). Time 37 minutes is the charter's stated total.
- Sanitary Permit: the charter total (20 min) conflicts with its 3-day inspection step, so the time shown is built from the steps ("3 days, 10 minutes") and a note says so. No fee is listed, so none is shown.
- Medical Certificate: display name corrects the source typo "Medial". The charter lists no documents (N/A), shown as "no documents listed", not invented.
- Referrals: time is the charter's total including the monthly monitoring hour; the four referral destinations stay in one step exactly as written.
- "Calendar or working days" is unknown in the charters; notes say the office does not specify.
- Display names are shortened for the mock ("Birth Registration (timely)"). The real API should send curated display names.
- Not in the contract yet: per-requirement "where to secure". Where-to-go chips use the section office plus offices in `related[]`.

## Stage 1 components (design page: `/design`)

Button, Chip, Segmented, LanguageToggle, DisplayControls (theme and text size), InfoScent, PendingBanner, OfflineBanner, SampleDataTag, ChecklistCard, ClarifyButtons, GroupChips, FallbackCard, Icon (own simple stroke icons, always decorative).

- Checklist: ticks are saved on the device (`cg.checklists.v1`) as soon as an item is ticked, or with "Keep this list on my phone". Progress ("3 of 9 ready") counts only items still on the current list. Storage errors are swallowed; the app works without storage.
- Settings (`cg.settings.v1`) are applied by an inline script in `index.html` before first paint to avoid a flash.
- Language choice is saved (`cg.lang`); default follows the phone (`fil` or `tl` -> Filipino).

## Stage 2: shell and home

- **Shell:** sticky header (monogram + name, EN/FIL toggle, "Aa" display button that opens theme and text size), a slim persistent "Thesis prototype, not an official government app" line, the offline banner, then the page. "Skip to main content" link first. The monogram is a plain blue rounded square with "CG": no seal, flag, sun or mascot.
- **Bottom nav:** three items (Ask, Saved, Help), 64px high, 16px labels. The current page has a top bar, bold text and `aria-current`, not colour alone.
- **Home order:** ask box ("What do you need to do?", Enter sends, Shift+Enter is a new line), topic chips by life event (Business, Family records, Health, Help and assistance; they filter and can be tapped again to clear), services grouped by life event, and offices last as secondary chips ("Or choose an office") that also filter.
- **Service row:** name, information scent line, office, chevron; the whole row is one 44px+ button. Pending services show "Being checked with the office" and no numbers. A row asks the chat the service's name (`navigate("/chat", { state: { message } })`; the chat screen is stage 3).
- **One small illustration** in the header of the ask box (a checklist sheet, palette tokens only). No hero, promo banner or badges.
- **Sample data tag** on the Services heading comes from `GET /health` (`mock: true`), because `/services` has no `meta`. `ApiClient` gained `health()`.
- **Errors:** loading failure shows the red alert card (the only use of red) with "Try again". Loading shows plain text with `aria-busy`.
- Task names use the API's service names as they are. Plain-language task phrasing ("Get a business permit") would be invented text for 40 services, so it waits for curated display names from the real API.

## Stage 3: chat and the answer card

- **Chat flow:** Home (or a tapped service row) navigates to `/chat` with the message in router state; Chat starts a new conversation, sends it, and clears the state so a reload does not resend. A bar above the bottom nav takes follow-ups (Enter sends). The session id from each response is sent back. A visually hidden `<h1>` and a `role="status"` line ("Looking it up" / "Answer ready") serve screen readers; the answer itself is not read out in a live region.
- **Conversation is kept** in memory (survives Ask/Saved/Help) and copied to `localStorage` (`cg.chat.v1`, last 20 turns). This is how "last answers" stay readable offline, without caching POSTs in the service worker. "New question" clears it. Answers stay in the language they were asked in; toggling FIL does not translate old answers.
- **Answer card order:** service name, summary line at key-fact size (from `summary`), notes, What to bring (tickable, progress "3 of 9 ready", saved on the device), What it costs, Steps timeline, Where to go, You will also need. One card per service. Notes come right under the summary, because "some items are only for some kinds of business" applies to the checklist.
- **Fees:** rows of label and amount; a total (from `summary.fee_text`) only when there is more than one fee. No fees means "The office does not list a fee... Ask the office before you go", never "free".
- **Steps:** numbered dots on a line, each step's time or "Time not listed", and "At another office" for external steps (for example payment at the City Treasurer's Office). Step text is the charter's own wording.
- **Where to go:** non-tappable office chips: the service's office plus offices in `related[]`. **You will also need:** "Go to {office} first", what is needed, and the API's note ("Get this first, then come back.").
- **Pending (`pending_lgu`):** name, "Being checked with the office", the calm banner and the office chip only. Checklist, fees, steps and related are not rendered even if the API sends them (test).
- **Clarify:** option buttons are live only on the latest reply; after a tap the choice appears as the citizen's message and the options disappear.
- **Fallback and refusal never dead-end:** a short honest message plus the four topic chips. Tapping a topic adds the services of that topic as clarify buttons, built from `GET /services` on the device (no API call), so a topic always leads to something.
- **Errors:** a failed send shows the red alert card with "Try again", which resends the same question.
- Motion is limited to a 200ms fade and 8px rise for each new message; it is skipped when the phone asks for reduced motion (MotionConfig and CSS).
- `/design` now also shows a confirmed and a pending answer card.

## Stage 4: saved lists, help, PWA and offline

- **Saved** (`/saved`): every checklist kept on the device (any ticked item, or "Keep this list on my phone"). Each is a card with name, office and "3 of 9 ready", expanding to the same tickable checklist (first one open). Removing asks first ("Remove this list?" / "Yes, remove" / "Keep it") in place, with no pop-up dialog. Empty state explains how a list gets here and offers "Ask a question". The page never calls the API, so it works with no signal. "There is no account" is stated on the page.
- **Help** (`/help`): the prototype notice first (yellow-tint note, navy text), then plain short blocks: what this is, how to use it in three steps, what "being checked" means, privacy (no login, no account; saved lists stay on the phone; questions are sent to the service to get an answer), using it without internet, sample data, and Display and language (EN/FIL, theme, text size).
- **PWA** (`vite-plugin-pwa`, Workbox `generateSW`, `registerType: "autoUpdate"`): manifest (standalone, blue theme colour and pale page background read from `tokens.json`, no hex duplicated), 192 and 512 icons, a maskable 512 and an apple-touch icon. Placeholder icon: plain blue rounded square with "CG"; no flag, sun or seal (test). Icons are rendered by `npm run icons` (sharp) from `public/icon.svg` and `public/icon-maskable.svg` and committed.
- **Offline behaviour:** the app shell (js, css, html, fonts, icons) is precached, with `/index.html` as navigation fallback (not for `/api/*`). `GET /api/services` is stale-while-revalidate. `POST /chat` is never cached; the last 20 turns are on the device (stage 3), so the last answers stay readable. Verified by building, installing the service worker, stopping the server and reloading `/saved`: the app opened.
- **Asking needs a signal.** Offline, the ask box, the send button and service rows are disabled and say why ("You are offline. You can still read your saved lists and your last answers."), so the sample fixtures cannot answer as if the API were reachable. The fixture fallback is for "API not running while online" (development without Python).
- **Bug found and fixed:** TanStack Query pauses requests while `navigator.onLine` is false, so the home screen would load forever when the app started offline. The query client now uses `networkMode: "always"` (`src/api/queryClient.ts`); a test covers a start with no signal.
- **Bundle:** one 530 kB chunk (164 kB gzip), precached once; the `/design` page is lazy-loaded. The Vite chunk warning limit is raised to 600 kB on purpose.
- **Not done:** an "update available" prompt (updates apply on the next visit), install prompt UI, and a real-device test on a low-end Android phone.
